Propuesta técnica — Sección Backend

Preparado por Ezequiel Viera, desarrollo backend. La sección de frontend la completa el equipo correspondiente.

Este documento cubre los dos frentes de trabajo definidos: la integración con la pasarela de pagos Handy y la incorporación del CRM de redes sociales (AloStudio). Para cada uno se detalla qué está decidido, qué está construido y qué queda pendiente.

1. Pasarela de pagos Handy

1.1 Situación

El acuerdo comercial con Handy ya está cerrado a nivel de dirección. Del lado técnico corresponde integrar la pasarela al sitio para poder cobrar los cursos en línea.

Hoy el sistema tiene integrada la pasarela de MercadoPago. MercadoPago no se retira: las dos van a convivir. Esto no es solo por prudencia — deja la puerta abierta a sumar una tercera pasarela si en el futuro se venden cursos al exterior, donde Handy no opera.

1.2 Decisión técnica: usamos el Botón de Pago

Handy ofrece dos formas de integrarse. Revisamos los manuales oficiales de las dos y optamos por la primera:

Botón de Pago Checkout API
Cómo funciona El alumno se redirige a una página de pago de Handy, como ocurre hoy con MercadoPago El formulario de tarjeta vive dentro de nuestro sitio
Tecnología API REST estándar Servicio Microsoft WCF, con firmado criptográfico de cada mensaje
Datos de tarjeta Nunca pasan por nuestro servidor Pasan por nuestro servidor
Esfuerzo de desarrollo Bajo Alto

Los dos motivos que definen la elección:

Riesgo regulatorio. El Checkout API recibe los datos de tarjeta directamente en nuestro servidor, lo que nos pondría dentro del alcance de la normativa PCI-DSS, con las auditorías y responsabilidades que eso implica. El Botón de Pago nos deja fuera: la tarjeta se ingresa en el entorno de Handy y nosotros nunca la vemos. Para una institución educativa que vende cursos, asumir esa responsabilidad no aporta nada.

Costo de desarrollo. El Checkout API está construido sobre Plexo, con una tecnología (WCF/SOAP) que exige firmar criptográficamente cada mensaje con un certificado digital, dar de alta comercios y negociar un código de comercio con cada sello por separado (Visa, Mastercard, OCA…). No existe librería para el lenguaje en que está hecho nuestro backend, por lo que habría que implementarlo a mano. El Botón de Pago se resuelve con un pedido HTTP estándar.

La diferencia práctica para el alumno es mínima: se lo redirige a una página segura de Handy y vuelve al sitio al terminar — exactamente la experiencia que ya tiene hoy con MercadoPago.

1.3 Medios de pago que habilita

La integración cubre todo lo que Handy ofrece hoy:

  • Tarjetas: Visa, Mastercard, OCA, Amex, Cabal, Passcard, Anda, Club del Este y Edenred
  • Redes de cobranza: Redpagos
  • Transferencias bancarias: Itaú, BROU, Scotiabank, BBVA y Bandes

Amex, Passcard y Edenred dependen del rubro que Handy tenga asignado a la institución — es una de las consultas pendientes.

1.4 Qué construye el backend

  1. Generación del cobro. Cuando el alumno decide comprar, el backend le pide a Handy un enlace de pago único con el detalle del curso y el monto, y lo redirige ahí.
  2. Recepción del resultado. Handy avisa por una notificación automática si el pago se concretó, quedó pendiente o falló. El backend procesa ese aviso y actualiza el estado.
  3. Registro propio de operaciones. Hoy el sistema no guarda ningún registro de los pagos: la integración con MercadoPago no persiste nada. Vamos a incorporar un registro propio de cada intento de cobro. Es imprescindible para conciliar contra los resúmenes de Handy, para resolver reclamos de alumnos y — como se explica abajo — para validar las notificaciones.
  4. Devoluciones. Handy permite devolver un pago una única vez, solo con tarjeta y hasta $10.000 / USD 250.

Un caso que conviene tener presente desde el diseño: los pagos por Redpagos no son inmediatos. Generan una orden con vencimiento que el alumno paga después en el local. Entre que elige el curso y efectivamente paga pueden pasar días, y en ese lapso el curso todavía no está pago. El sistema maneja ese estado intermedio.

1.5 Pendiente: respuestas de Handy

Ya enviamos la consulta técnica a Handy y nos derivaron al área de integraciones. A la fecha seguimos sin respuesta.

Hay dos preguntas cuya respuesta condiciona el diseño de seguridad:

  1. ¿Cómo validamos que una notificación de pago viene realmente de Handy? El manual publicado no documenta ningún mecanismo de firma o autenticación para esos avisos. Tal como está documentado, alguien que descubriera la dirección de nuestro sistema podría enviar un aviso falso de "pago exitoso".
  2. ¿Existe forma de consultarle a Handy el estado de un pago? El manual describe cómo crear un cobro y cómo devolverlo, pero no cómo preguntar si una operación está efectivamente paga. Sin esa consulta no tenemos contra qué verificar el aviso recibido.

Puede tratarse simplemente de funcionalidad no documentada en el manual público. Con que exista cualquiera de las dos, el problema se resuelve de forma directa y estándar.

Si la respuesta fuera que no existe ninguna, la integración se puede hacer igual aplicando medidas compensatorias de nuestro lado: dirección de notificación secreta, verificación contra nuestro propio registro de operaciones, control de duplicados y registro completo de todo lo recibido. En ese escenario conviene que la dirección esté al tanto de que existe un riesgo residual asumido a conciencia.

1.6 Qué se puede avanzar mientras tanto

La espera no bloquea todo el trabajo. El registro de operaciones, la generación del enlace de pago y el flujo de compra se pueden construir y probar contra el ambiente de pruebas de Handy, que ya está disponible y documentado. Lo único que queda supeditado a la respuesta es la capa de validación de las notificaciones.

Para salir a producción sí hacen falta las credenciales definitivas, que se solicitan por el mismo canal.

2. CRM de redes sociales (AloStudio)

2.1 Qué problema resuelve

Hoy las consultas de posibles alumnos llegan dispersas: mensajes de Instagram, WhatsApp, correo y formularios del sitio. Cada canal se atiende por separado, no queda historial unificado por persona y no hay forma de medir cuántas consultas terminan en una inscripción.

El CRM centraliza todos esos canales en una única bandeja de entrada, con historial completo por contacto, asignación a responsables y métricas de atención.

2.2 Estado: el backend ya está construido

Este no es un desarrollo a iniciar desde cero. El backend es un sistema ya funcionando, construido sobre Chatwoot — una plataforma de atención al cliente de código abierto y ampliamente adoptada — reimplementada en la misma tecnología que usa el backend de CTC, lo que facilita el mantenimiento por parte del mismo equipo.

Dimensiones actuales del sistema:

Endpoints de API222
Tablas de base de datos62
Módulos funcionales38
Archivos de pruebas automatizadas166

Sobre esa base se agregaron desarrollos propios que no forman parte de Chatwoot: el módulo de Instagram, el catálogo de productos y servicios, la sincronización de métricas de Meta Ads y un servidor de integración para agentes de inteligencia artificial.

2.3 Canales de comunicación soportados

  • Instagram — mensajería, comentarios y publicación (es el módulo más desarrollado)
  • WhatsApp
  • Facebook Messenger
  • Correo electrónico — con lectura automática de casilla
  • Widget web — chat embebido en el sitio institucional
  • Telegram, SMS y Twilio

2.4 Qué incluye el backend

Gestión de la atención

  • Bandejas de entrada por canal, con conversaciones y estados
  • Contactos con historial unificado y atributos personalizados
  • Equipos, asignación automática y políticas de distribución de carga
  • Horarios de atención y respuestas fuera de hora
  • Respuestas predefinidas y macros para tareas repetitivas
  • Etiquetas y vistas personalizadas
  • Reglas de automatización

Medición

  • Reportes de atención: volumen, tiempos de respuesta y resolución
  • Encuestas de satisfacción (CSAT)
  • Sincronización de métricas de campañas publicitarias de Meta Ads

Módulo de Instagram (desarrollo propio)

  • Publicación de imágenes, videos, reels, carruseles e historias
  • Programación de publicaciones para fecha y hora futura
  • Moderación de comentarios
  • Recepción de eventos en tiempo real (comentarios, menciones, métricas)
  • Catálogo de productos y servicios vinculado a las publicaciones

Base técnica

  • Actualizaciones en tiempo real en la interfaz, sin necesidad de recargar
  • Procesamiento en segundo plano para tareas pesadas y programadas
  • Control de acceso por roles y por cuenta

2.5 Cómo se integra con los sistemas de CTC

El CRM está preparado para integrarse con sistemas externos por tres vías, ya implementadas:

  1. API REST — permite consultar y modificar información desde otro sistema.
  2. Notificaciones automáticas — el CRM avisa a CTC cuando ocurre algo relevante: se crea un contacto, entra una conversación, cambia su estado o llega un mensaje.
  3. Servidor de integración para agentes de IA — permite que un asistente automático lea conversaciones y responda, con permisos acotados (solo lectura, lectura y escritura, o administración) y credenciales revocables por cuenta.

Esta última vía es la que abre la posibilidad de un asistente que responda consultas frecuentes sobre cursos, horarios y requisitos fuera del horario de atención, escalando a una persona cuando corresponda. Es una capacidad disponible, no un desarrollo pendiente.

2.6 Qué queda por hacer del lado del backend

El sistema está construido; lo que resta es el trabajo específico de adaptarlo a CTC:

  • Despliegue e infraestructura — puesta en producción del sistema y sus servicios asociados.
  • Credenciales de Meta — alta de la aplicación de Instagram y Facebook a nombre de la institución, y proceso de verificación ante Meta. Es un trámite externo con plazos que no dependen de nosotros, conviene iniciarlo temprano.
  • Conexión con el sistema de CTC — definir qué información se comparte entre el CRM y el Portal Académico, y en qué sentido.
  • Carga inicial — usuarios, equipos, horarios de atención y respuestas predefinidas.

3. Cómo se conectan los dos puntos

Aunque son dos frentes independientes, juntos completan el circuito comercial de un curso de principio a fin:

Etapa Sistema
Un interesado consulta por Instagram o WhatsApp CRM
La consulta queda registrada como contacto, con su historial CRM
Se le envía el enlace de pago del curso Handy
El pago se acredita y queda registrado Backend CTC
Se habilita la inscripción del alumno Portal Académico

Hoy ese recorrido está cortado en varios puntos y cada tramo se resuelve a mano. Cerrarlo permite saber cuántas consultas se reciben, cuántas terminan en una venta y por qué canal llegan — información que hoy no existe.

Ese es también el motivo por el que conviene incorporar el registro propio de pagos descrito en el punto 1.4: es la pieza que conecta el cobro con la inscripción.

4. Resumen

Decidido

  • Handy se integra mediante el Botón de Pago, no el Checkout API
  • MercadoPago se mantiene y ambas pasarelas conviven
  • Se incorpora un registro propio de operaciones de pago, hoy inexistente
  • El backend del CRM ya está construido; resta el trabajo de adaptación e integración

Pendiente de terceros

  • Handy — respuesta del área de integraciones a las consultas técnicas de seguridad, y entrega de credenciales de producción
  • Meta — alta y verificación de la aplicación de Instagram y Facebook a nombre de la institución

Pendiente de definición interna

  • Si el pago de un curso debe habilitar automáticamente la inscripción en el Portal Académico, o se mantienen como procesos separados
  • Qué información se comparte entre el CRM y el sistema de CTC

Los plazos de la integración con Handy se pueden estimar con precisión una vez que respondan las consultas técnicas, dado que de ello depende el alcance del trabajo de validación.
